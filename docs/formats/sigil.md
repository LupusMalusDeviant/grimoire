# Sigil Format — Source Syntax `sigil 1`

Hand-written (not generated by `grimoire_schemagen`): the source-syntax grammar comes from engine
[ADR-0007](../adr/0007-sigil-quelltextsyntax-v1.md), not a `schema/*.gschema` file. Implemented in
`grimoire_sigilc` (`crates/grimoire_sigilc/src/lexer.rs`, `syntax.rs`, `parser.rs`, `fmt.rs`,
Plan 0002 WP4.1). This page describes what that code does, not what it should do; a divergence
between this page and the crate's behaviour is a bug in one of the two.

Sigil source version **1** (`sigil 1`). The binary unit format `SigilUnit` this compiles to
(engine contract §11.1) is versioned separately and documented in its own section of this file
once the encoder lands (Plan 0002 WP4.2) — the two version numbers are unrelated, by design
(ADR-0007).

**Scope of this page (WP4.1):** lexing, parsing, the lossless syntax tree, node paths and the
lexer/parser diagnostics. **Not covered here** (Plan 0002 WP4.2 and later): the schema pass (which
field names, kinds, units and ranges are valid for which construct), name resolution and imports,
the `SigilUnit` binary encoding, and the `sigilc build`/`set`/`migrate`/`simulate` subcommands. A
file that is syntactically valid by this page's rules can still be rejected by the schema pass —
`sigilc check`/`parse --json` in WP4.1 only ever raise the codes in the table below.

## 1. Overview

A `.sigil` file is UTF-8 text: a mandatory one-line version header, then zero or more **items**
(`import`, `meta`, `bullet`, `emitter`), each ending at a blank line or the next item. Item bodies
are brace-delimited and line-oriented — one field or nested member per line — so that a
[parser diagnostic](#5-diagnostics) always has a natural line to point at, and a value edit
(`sigilc set`, Plan 0002 WP4.3) touches exactly one line.

The parser builds a **lossless concrete syntax tree**: every byte of the source, including
whitespace, comments and blank lines, ends up as exactly one token in the tree, in source order.
Formatting an unmodified tree (`grimoire_sigilc::format`) reproduces the source byte-for-byte; see
[`tests/roundtrip.rs`](../../crates/grimoire_sigilc/tests/roundtrip.rs) for the property tests
that check this. This is what lets a later tool rewrite a single value without disturbing the
rest of the file.

The parser never panics, regardless of the input (contract §2 rule 9): malformed input becomes
[diagnostics](#5-diagnostics) collected alongside the (still complete) tree, not a crash and not a
single fatal error. Where the parser cannot make sense of a construct at all, it wraps the
offending tokens in an opaque "error" tree node and keeps going, so a file can, and usually does,
come back with more than one diagnostic.

## 2. Lexical grammar

Source files are UTF-8 without a byte-order mark. Columns in diagnostics count Unicode scalar
values (`char`s), starting at 1; lines start at 1.

```text
newline      = [ "\r" ], "\n"
space        = " " | "\t"
comment      = "//", { any character except "\n" }

letter       = "a".."z" | "A".."Z"
digit        = "0".."9"
ident        = ( letter | "_" ), { letter | digit | "_" }

int_lit      = [ "-" ], digit, { digit }
float_lit    = [ "-" ], digit, { digit }, ".", digit, { digit }
number       = float_lit | int_lit

unit         = "deg/t" | "deg" | "u/t2" | "u/t" | "u" | "t" | "beats"
quantity     = number, unit                      (* no space between number and unit *)

string       = '"', { string_char | escape }, '"'
string_char  = any character except '"', "\", "\n"
escape       = "\", ( '"' | "\" | "n" | "t" )

punctuation  = "{" | "}" | "(" | ")" | "[" | "]" | "=" | "," | "."
```

- **Comments** are `//` to the end of the line (the newline itself is a separate token). They are
  trivia: a comment may stand on its own line or trail a construct, anywhere, including inside the
  header line.
- **Newlines are significant** (a real token that ends an item or a body member) at bracket depth
  0; a newline found inside `(...)` or `[...]` is trivia instead, so a list or record literal may
  span multiple lines. Braces never change the bracket depth.
- **Units** are matched by taking the longest run of lowercase letters, digits and `/` immediately
  after a number (no space): `0.09u/t`, `30t`, `0.5deg/t`. If that run is not exactly one of the
  units above, the token is still lexed as one `Quantity` (so a diagnostic can point at the whole
  thing, e.g. `30s`), and the parser raises [`SIG0006`](#sig0006). `beats` is lexically valid but
  reserved: it lexes without a diagnostic in WP4.1, and a later schema pass (WP4.2) rejects it —
  there are no wall-clock units (`ms`, `s`) in Sigil at all.
- **Keywords are contextual.** `sigil`, `import`, `as`, `meta`, `bullet`, `emitter`, `from`,
  `block`, `modifier`, `transform`, `time`, `distance` and `event` all lex as plain identifiers;
  the parser only treats one as a keyword in the specific grammar position below. `bullet = orb`
  is a valid field inside an emitter body even though `bullet` is also an item keyword.
- An unrecognised byte becomes a single-character token rather than being skipped, so the tree
  stays lossless even over garbage input; the parser then reports it wherever it was expecting
  something else ([`SIG0008`](#sig0008)).

## 3. Header

Line 1, column 1, must be exactly:

```text
sigil <N>
```

with no byte-order mark and no comment before it — not even on the same line. `<N>` is checked
before anything else is parsed:

- Missing, preceded by a byte-order mark or a comment, or not starting with the literal `sigil`:
  [`SIG0001`](#sig0001), pointing at line 1 column 1. Nothing else in the file is parsed further.
- Present but `<N>` is not the literal integer `1` (a different number, a float, or missing
  entirely): [`SIG0002`](#sig0002), pointing at whatever follows `sigil`. Nothing else in the file
  is parsed further.
- Anything else on the header line after `<N>`, before its newline: `SIG0001` at that content, and
  the rest of the line is skipped; parsing then continues normally with the next line.

Either failure produces **exactly one** diagnostic for the whole file — this is deliberate
(ADR-0007): a version mismatch is not worth cascading into dozens of "unexpected token" findings
from content this compiler cannot promise to understand at all.

## 4. Syntactic grammar

```text
file          = header, { NEWLINE }, { item, item_end }
item_end      = ( NEWLINE, { NEWLINE } ) | EOF

item          = import_item | meta_item | bullet_item | emitter_item
import_item   = "import", string, "as", ident
meta_item     = "meta", body
bullet_item   = "bullet", ident, body
emitter_item  = "emitter", ident, [ "from", ref ], body

body          = "{", { NEWLINE }, { member, NEWLINE, { NEWLINE } }, "}"
member        = field | nested
field         = path, "=", value
nested        = ( "block" | "modifier" | "transform" ), ident, body
path          = ident, { ( ".", ident ) | ( "[", int_lit, "]" ) }

value         = quantity | float_lit | int_lit | string | trigger | ref | list | record
trigger       = ( "time" | "distance" | "event" ), ( quantity | ref )
ref           = ident, { ".", ident }
list          = "[", [ value, { ",", value }, [ "," ] ], "]"
record        = "(", [ record_field, { ",", record_field }, [ "," ] ], ")"
record_field  = ident, "=", value
```

Notes on how the parser applies this grammar, not just what it accepts:

- **Member position** is decided with a small, fixed lookahead: `ident` followed by `"="` (or by
  a `.`/`[` path continuation and then `=`) is a field; `("block"|"modifier"|"transform")` followed
  by `ident` and then `"{"` is a nested member; anything else is a parse error
  ([`SIG0008`](#sig0008)). Because a field is checked structurally, `block = foo` (using `block`
  as a bare field name) parses as an ordinary field, not a malformed nested member.
- **One member per line.** Two fields (or a field and a nested member) on the same line without a
  separating newline is a parse error ([`SIG0008`](#sig0008)); the second one is still parsed as
  its own member on the next parser iteration, so this costs exactly one diagnostic.
- **A trailing comma is allowed** in a list or a record; a doubled comma, or a leading comma
  before the first value/field, is [`SIG0009`](#sig0009).
- **Resynchronisation.** If a body's `}` is missing, the parser stops that body as soon as it sees
  either end-of-file or something that unambiguously starts a *new* item — `import "..."`, `meta
  {`, or `bullet`/`emitter` followed by a name — reporting [`SIG0007`](#sig0007) once, with a
  related location pointing at the unmatched `{`. The same rule applies to an unclosed list or
  record ([`SIG0011`](#sig0011)): a stray `}` or the start of a new item stops it there rather than
  being swallowed as if it were more list/record content, so one missing `]`/`)` costs one
  diagnostic, not a cascade through everything that follows. Two items placed on the same line
  with no separating newline at all (`meta {} bullet x { ... }`) is accepted without a diagnostic
  in WP4.1 — a known, minor leniency; see [§7](#7-known-limitations-wp41).
- **Nesting is bounded.** Bodies, lists and records may nest at most 64 levels deep combined
  (counting into a nested `block`/`modifier`/`transform`'s own body as one more level, same as a
  list inside a record inside a list); past that, parsing stops descending into that subtree with
  one [`SIG0010`](#sig0010) instead of recursing further, so pathological input cannot overflow
  the stack. No real pattern comes close: the ADR's own emitter cascade-depth limit is 3.

## 5. Node paths

Every diagnostic names a **node path**: which item, and which field or nested member inside it,
the diagnostic is about. Node paths need no schema or name resolution (out of scope for WP4.1) —
they follow purely from an item's own keyword and name, and from a purely positional count of how
many `modifier`/`transform` members a body has seen so far when the parser reaches one:

| Path shape | Example | Meaning |
|---|---|---|
| `version` | `version` | The header itself. |
| `meta` | `meta` | Inside the `meta` item's body. |
| `meta.<path>` | `meta.density` | A field of `meta` (or, dotted/indexed, a path inside it: `meta.difficulty[1]`). |
| `imports` | `imports` | Inside an `import` item. |
| `bullets.<name>` | `bullets.seed` | Inside a `bullet <name>` item's body. |
| `bullets.<name>.<path>` | `bullets.seed.radius` | A field of that bullet. |
| `bullets.<name>.transforms[<i>]` | `bullets.seed.transforms[0]` | The `i`-th (0-based) `transform` member of that bullet, in written order. |
| `emitters.<name>` | `emitters.burst` | Inside an `emitter <name>` item's body. |
| `emitters.<name>.block` | `emitters.burst.block` | The (at most one) `block` member of that emitter. |
| `emitters.<name>.block.<path>` | `emitters.burst.block.count` | A field inside that block, or (via a dotted override field, e.g. `block.count = 12` in an `emitter ... from ...` body) the same path without a literal nested `block` member at all. |
| `emitters.<name>.modifiers[<i>]` | `emitters.burst.modifiers[0]` | The `i`-th (0-based) `modifier` member of that emitter, in written order. |
| `emitters.<name>.modifiers[<i>].<path>` | `emitters.bloom.modifiers[2].keys` | A field inside that modifier. |

`block` is never indexed (a body has at most one — the schema pass, WP4.2, enforces that count;
WP4.1's parser accepts any number syntactically and just numbers a second `block` member's fields
under the same unindexed `block` path). `modifier` and `transform` are always indexed by how many
members of that same keyword the enclosing body has already seen, regardless of what kind each one
is (`block ring { ... }` and `block fan { ... }` are both just "the block"; `modifier rotate { }`
then `modifier mirror { }` are `modifiers[0]` and `modifiers[1]`).

## 6. Diagnostics

Every diagnostic carries a file, a 1-based line and column, a [node path](#5-node-paths), the
exact offending token's text, a cause, a fix hint, a stable code, and — for an unmatched
delimiter — a related location pointing at the delimiter it fails to match. A file can raise more
than one diagnostic; the parser only stops entirely after a bad [header](#3-header).

### 6.1 Text form

`sigilc check <file>...` prints one block per diagnostic:

```text
<file>:<line>:<column>: error[<code>]: <message>
  at <node_path>
  fix: <fix_hint>
  related: <label> at <file>:<line>:<column>: `<token>`
```

The `at` line is omitted when the node path is empty (only possible for a diagnostic about the
header itself, which uses the path `version`, so in practice `at` is always present); `fix` is
omitted when there is no fix hint; `related` is omitted unless the diagnostic has one.

### 6.2 JSON form

`sigilc parse --json <file>` prints one JSON document (contract §2 rule 11: UTF-8, no BOM, fixed
key order, integers as JSON numbers only within ±2^53−1 — true here, since line/column/schema
version are all small):

```json
{
  "schema_version": 1,
  "file": "path/as/given/on/the/command/line.sigil",
  "diagnostics": [
    {
      "code": "SIG0006",
      "severity": "error",
      "file": "path/as/given/on/the/command/line.sigil",
      "line": 3,
      "column": 11,
      "node_path": "emitters.burst.delay",
      "token": "5s",
      "message": "Unknown unit `s` on `5s`.",
      "fix_hint": "Use one of the known units: deg/t, deg, u/t2, u/t, u, t, beats.",
      "related": null
    }
  ]
}
```

`severity` is always `"error"` in WP4.1 (see [`Severity`](../../crates/grimoire_sigilc/src/diagnostics.rs)'s
doc comment for why the enum already has room for `"warning"`). `related`, when present, is
`{ "label", "line", "column", "token" }` for the secondary location.

### 6.3 Diagnostic code table

Codes are stable from their first release (this table): a code, once shipped, keeps its meaning
even if `message`/`fix_hint` wording later improves. `SIG0005` is reserved (no lexer/parser
condition currently uses it); the schema pass (Plan 0002 WP4.2) continues the sequence from
`SIG0012`.

| Code | Cause |
|---|---|
| `SIG0001` | Missing or malformed version header: not exactly `sigil <N>` as the first line, column 1, with nothing before it; or unexpected content after `<N>` on the header line. |
| `SIG0002` | The header names a version other than `1` (a real future version is expected to move this compiler's supported line forward, not raise a new code). |
| `SIG0003` | A string literal is not closed with `"` before the line (or the file) ends. |
| `SIG0004` | A `\` inside a string literal is followed by a character other than `"`, `\`, `n` or `t`. |
| `SIG0006` | A number's unit suffix is not one of `deg/t`, `deg`, `u/t2`, `u/t`, `u`, `t`, `beats`. |
| `SIG0007` | A body opened with `{` is not closed with `}` before end-of-file or the next item. |
| `SIG0008` | A generic "expected X, found Y" parse error: a wrong or missing token where the grammar needs a specific one (a field's `=`, an item's name, `{` to start a body, one member per line, and so on — the message always names what was expected and what was found). |
| `SIG0009` | A doubled comma, or a leading comma before any value/field, inside a list or a record (a single trailing comma is allowed). |
| `SIG0010` | A body, list or record nests more than 64 levels deep; parsing stops descending into it instead of recursing further. |
| `SIG0011` | A list or record opened with `[`/`(` is not closed with `]`/`)` before end-of-file, an enclosing body's `}`, or the next item. |

## 7. Known limitations (WP4.1)

- Two items placed on the same line with no separating newline at all (e.g. `meta {}bullet x {
  radius = 1u }`) parse without a diagnostic, even though the grammar in [§4](#4-syntactic-grammar)
  requires a newline there. The same rule *is* enforced one level down, between two members inside
  one body (`count = 24 start = 7.5deg` on one line raises `SIG0008`) — that shape was measured
  and named explicitly as a required error case in ADR-0007's acceptance conditions. The
  item-level gap is a low-priority, disclosed follow-up, not a silent one; see the pull request
  description for the recommendation.
- The lexer's unit-suffix scan only ever consumes lowercase ASCII letters, digits and `/`
  immediately after a number; `30 t` (a space before the unit) lexes as a bare integer `30`
  followed by a separate identifier `t`, which then fails wherever the grammar expected a newline
  or `=`, with a generic `SIG0008` rather than a message naming the missing-space mistake
  specifically. The file still comes back with a correct, if generic, diagnostic.

## 8. Example files

### 8.1 A ring-burst pattern (`tests/corpus/valid/01-ring-burst.sigil`)

```text
sigil 1
// 01-ring-burst: repeated ring burst whose bullets accelerate outwards.
// Covers: block ring, modifier accelerate, flags smashable + grazeable, visual metadata
//         (silhouette, palette, glow), despawn_vfx, emitter delay/repeat/interval, meta.

meta {
  name = "Ring Burst"
  difficulty = [easy, opener]
  density = 96 // estimated bullets on screen at peak
}

// Slow round orb; melee can smash it, grazing charges the ultimate.
bullet orb {
  silhouette = orb
  palette = enemy.crimson
  glow = 0.6
  radius = 0.25u
  damage = 1
  flags = [smashable, grazeable]
  despawn_vfx = soul_wisp // played on bullet clear (FR-12)
}

emitter burst {
  bullet = orb
  delay = 30t // telegraph time before the first ring
  repeat = 4
  interval = 45t
  speed = 0.05u/t
  block ring {
    count = 24
    start = 7.5deg // offset from the cardinal axes
  }
  modifier accelerate {
    rate = 0.002u/t2
    max_speed = 0.2u/t // cap keeps late bullets readable
  }
}
```

### 8.2 Composition via `import` and overrides (`tests/corpus/valid/05-wave-line-composite.sigil`, excerpt)

The full file is in the conformance corpus; this excerpt shows the header, an import, a trigger
(`event phase_end`), a behaviour reference, and an emitter defined `from` another file's emitter
with dotted-path overrides — every value-shape category in [§4](#4-syntactic-grammar) except a
`record`, shown in §8.1's `flags = [...]` sibling example above and in `02-aimed-stream.sigil`'s
`offset = (x = 0u, y = -0.5u)`.

```text
sigil 1
import "01-ring-burst.sigil" as ring

meta {
  name = "Tide and Rail"
  difficulty = [normal, mixed]
  density = 220
  patron = ember_court
}

bullet blade {
  silhouette = blade
  palette = enemy.teal
  glow = 0.5
  radius = 0.3u
  damage = 2
  flags = [env_active, reflectable]
  transform reverse {
    when = event phase_end // all blades turn around when the boss phase ends
  }
}

bullet satellite {
  silhouette = crescent
  palette = enemy.teal
  glow = 0.9
  radius = 0.2u
  damage = 1
  flags = [grazeable]
  behaviour = orbit_parent
}

// Reuses the ring emitter of 01-ring-burst; only the listed parameters differ.
emitter finale from ring.burst {
  delay = 240t
  repeat = 1
  block.count = 12
}
```

## 9. Conformance corpus

`crates/grimoire_sigilc/tests/corpus/` holds the machine-checked conformance corpus (Plan 0002
WP4.1 requirement 5): plain `.sigil` files under `valid/` (must parse with zero diagnostics) and
`invalid/` (must parse with at least one), each paired with a `<name>.expected.json` sidecar in
exactly the [§6.2 JSON form](#62-json-form) — literally what `sigilc parse --json <file>` prints
for it. `crates/grimoire_sigilc/tests/corpus.rs` checks this crate's own parser against every
sidecar; the same `.sigil`/`.expected.json` pairs are plain data with nothing Rust-specific about
them, so a later C# asset-compiler test (this corpus's stated purpose) can run the same files and
compare against the same sidecars independently.
